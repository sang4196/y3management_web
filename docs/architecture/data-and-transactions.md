# 데이터 접근·트랜잭션·권한 초안

2026-10-12 승인 정책 반영 경계: [2026-10-12 일괄 승인](../product/product-decisions.md#review-20261012-batch)과 ADR-0004 v1 인증 방식 ACCEPTED를 입력으로 사용한다. B/A 정책 승인으로 이 문서의 모듈 소유권·공개 계약·DB 직접 접근 예외·Caller/저장/UoW/잠금이 채택되는 것은 아니다. 직접 다른 모듈 DB 읽기 예외 **현재 승인 0건**을 유지한다. 새 Pass 활성 담당 필수/상품 최초 횟수·관리자 초과 잔여 추가, Branch 비활성 신규 업무 차단, 공통 Asia/Seoul 및 로그인/역할 철회 정책을 이후 계약/원자성/경합 검증에 반영해야 한다. 실제 구현/DB 검증은 이번에 수행하지 않았다.

Status: PROPOSED
작성일: 2026-09-17
업무 원자성·권한·과거 결과 보존은 이미 Product 요구다. 이를 만족시키는 아래 UoW(Unit of Work: 한 업무의 변경을 함께 완료/취소하는 경계)·계약·일관성 전략은 제안이다. SQL·schema·잠금 방식·격리 수준·멱등성 키 구조는 확정/구현하지 않는다.

## 데이터 접근 규칙

2026-10-11 Product 확정(BR-OPS-001/BR-PAY-006): 같은 Organization의 사용 가능한 Pass를 타 지점에서 쓸 때 별도 사전 승인을 두지 않는다. Issued Branch=Performed Branch를 필수 조건으로 삼거나 발급 지점 승인 대기·발급 지점 우선 선택을 추가하지 않는다. 요청 Actor의 PT 업무 권한·Organization/Member/Pass 관계·사용 가능 조건은 별도로 검증한다. 교차 이용 가능 사실을 타 지점 전체 자료 접근 권한으로 사용하지 않는다. 관련 조회/인가 계약·트랜잭션 구조는 PROPOSED이며 나머지 Actor/Member 조회 범위는 MB-001/002/003/005 게이트다.

[소유권 표](module-boundaries.md)의 단일 소유 모듈만 업무 데이터를 변경한다. 다른 모듈 Repository 직접 호출, 다른 모듈 ORM 객체 수정, 공개 계약으로 SQLAlchemy Session/지연 로딩 ORM 반환을 금지하는 방향을 제안한다. 계약은 필요한 ID·값·업무 결과/검증 근거만 명시한다. 보상 설정의 일반 관리 조회와 허용 Session 계산용 내부 소비는 별도 계약으로 제한한다.

FastAPI Router는 입력 검증·Actor 전달·응답 변환을 담당하고 핵심 규칙은 Use Case와 소유 모듈에서 실행한다. 도메인/Use Case는 FastAPI Request/Depends를 알지 않는다. DB 어댑터는 SQLAlchemy를 사용하되 모듈 계약으로 ORM을 누출하지 않는다. 저장소별 commit/rollback을 두지 않고 최상위 Application Use Case만 최종 성공/실패를 결정한다.

같은 업무에 참여하는 각 모듈의 DB 어댑터를 같은 PostgreSQL 트랜잭션에 연결하는 구성을 제안한다. 논리적 모듈이 다르다고 별도 DB 세션을 열어 독립 commit하지 않는다. UoW 조립부가 수명을 관리하고 공개 업무 계약에는 SQLAlchemy Session을 넘기지 않는다. 동기/비동기 선택 이후 구체 연결 방식을 검증해야 한다. 하나의 SQLAlchemy 세션을 동시 task/thread에서 공유하는 구현은 피한다([ADR-0001](../decisions/0001-backend-stack.md)의 공식 근거).

DB 참조 제약은 현재 정합성 필요에 따라 후속 설계한다. 미래 추출을 이유로 FK를 일괄 제거하지 않으며 cross-module 참조 제약을 쓰게 되면 의존성과 추출 비용을 기록한다. 지금 테이블·컬럼·키는 지정하지 않는다.

2026-10-12 사용자 확정(Operator 업무 허용 지점 수 질문의 1번): v1 Operator 역할의 업무 허용 Branch는 한 시점에 하나만 지정한다. Operator는 그 지정된 단일 Branch에서 명시적으로 허용된 업무를 수행하며 같은 계정의 Operator 권한을 여러 Branch에 동시 부여하지 않는다. Branch당 Operator 한 명이라는 1:1 인원 제한을 추가하지 않으며 하나의 Branch에 여러 Operator가 있을 수 있다. 이 결정은 Operator 역할의 업무 Scope이며 기존에 허용된 겸임 역할의 독립적인 관리/PT 권한이나 Trainer Home Branch를 바꾸지 않는다(BR-OPS-011, PD-001/007, PR-001/003/030, ARCH-001, MB-004).

인가 경계: Backend는 검증된 현재 Caller의 Operator 역할/Organization·지정된 단일 업무 Branch와 해당 요청의 실제 업무 Branch를 확인한다. 직접 Branch ID·클라이언트 branch_id/role/선택 지점·과거 업무/발급 지점만으로 다른 Branch의 업무를 수행할 수 없다. 동일 계정에 Operator 권한을 중복 부여하거나 여러 Branch 중 하나를 임의 선택하는 방식으로 단일 지점 제한을 우회하지 않는다. 현재 역할/Scope 철회·축소 이후 후속 요청은 현재 권한을 적용한다. 지정이 없거나 복수 지정된 상태를 유효한 Operator 업무 권한으로 간주하지 않되 구체 계정/역할 저장·활성화 제약과 오류 계약은 후속 Architecture다.

기존 발급/검색 규칙 유지: Operator의 새 Pass 발급은 자신의 지정된 단일 Branch를 실제 Issued Branch로 사용한다. 그 발급 업무에서는 같은 Organization 전체 지점 Member를 이름·전화번호 일부로 검색하고 결과의 이름·전체 전화번호·현재 Member Home Branch를 조회/선택할 수 있다(BR-OPS-010). Member Home Branch가 Operator 업무 Branch와 다르다고 검색/발급을 거부하거나 회원 소속을 자동 이동하지 않는다. 전체 지점 Member 검색이 다른 Branch의 Pass 발급이나 일반 회원 상세/다른 Pass/PT·보상/수정·일괄 내보내기 권한을 부여하지 않는다. 기존 Master 전용 공통 상품 변경 및 관리자 전용 Pass 수동 조정·만료/해제·담당 교체/보상 업무 제한은 유지한다.

설계 후속(PROPOSED): IAM은 검증된 현재 Caller에 Operator의 단일 업무 Branch 사실을 제공하고 Organization의 Branch/Organization 사실과 해당 업무 인가를 조합한다. 동일 계정의 복수 Operator Branch를 우회 Scope로 해석하지 않도록 저장/Caller/인가 계약·동시 부여/변경 정합성을 설계한다. 구체 FK/유일성·역할 테이블·잠금/SQL·UoW/API는 확정하지 않는다. 단일 업무 Branch와 발급용 Organization 전체 지점 Member 후보 검색을 구별하고 Membership의 승인된 최소 검색/공개 계약으로 조합한다. 다른 모듈 Repository/ORM·DB 직접 접근 예외와 S1 Operator 구현을 추가하지 않는다. 남은 결정: 새 Operator 발급/최초 Branch 지정 Actor는 Master Organization 전체/Branch Admin 자기 단일 Branch, 기존 Operator 업무 Branch 변경 Actor는 Master Organization 범위 전용으로 해결됐다. 변경은 기존 저장 후 현재 Scope 반영/실패 보존·감사 원칙을 적용한다. 발급 절차·기존 계정 역할 추가/변경·Operator 지점 변경의 대상 Branch/계정 상태·세부 절차/감사 계약 및 나머지 운영 행위 권한은 MB-004·ARCH-001/002 후속이다. 한 계정의 Operator 동시 허용 지점 수나 신규 발급/지점 변경 Actor를 다시 OPEN으로 두지 않는다. 실제 발급 대상·초기 조건/선택 응답·역할/Scope 저장·Caller/인가 계약·실패/재시도/경합은 관련 Product/Architecture 후속이다. IAM-001 S1에 Operator 구현을 추가하거나 기존 PROPOSED 인증/모듈/저장 설계를 승인한 것은 아니다.

2026-10-12 G 일괄 승인과 기술 경계: 비활성 Branch에 관한 G1–G5는 현재 행위별 권한과 유효 인증·실제 Trainer 활성/담당·지원·Pass 가용 조건을 함께 검증하는 정책이다. 실제 Performed Branch가 비활성인 기간의 새 수업은 차단하고, 비활성화 전 수업은 당시 운영/소속/담당/수행 사실과 현재 인가·실제 진행 월 정산 상태를 구분한다. 다른 활성 지점에서 기존 Pass 사용/소속 비활성 Member·활성 Trainer 수업은 허용하며 현재 Home/Issued Branch의 비활성을 단일 전역 거부 조건으로 삼지 않는다. 명시적 이동은 기존 Actor/Scope·즉시 적용/실패 보존·감사/과거 보존을 따른다. 현재 사실과 역사 사실 조회·상태 변경/차감/이동/확정의 순서·UoW/잠금은 후속 PROPOSED로 실제 PostgreSQL 경합 검증이 필요하다. 직접 타 모듈 DB 읽기 예외 **현재 승인 0건**을 유지한다. [2026-10-12 G 일괄 승인](../product/product-decisions.md#review-20261012-g-batch).

## 통합 조회와 직접 읽기 예외

Trainer 회원 검색/조회(2026-10-12 Product 확정, BR-OPS-005·PR-002/029/030): 대상은 본인 담당 Trainer로 지정된 Pass의 Member 또는 해당 Trainer에 대해 개별 허용된 지원 Member다. 같은 Home Branch/Organization 전체 조회를 허용하지 않고 목록·검색·직접 ID 상세마다 검증된 Caller의 Trainer 연결/Organization Scope와 관계 사실을 확인한다. 담당 Pass/지원 허용 사실과 Member 조회를 소유 모듈의 공개 계약으로 조합하고 허용 대상에 필요한 정보를 반환하는 Application 인가/조회 계약을 후속 설계한다(PROPOSED). 지원 허용의 저장 소유 모듈·테이블/역할 모델을 이번 결정으로 확정하지 않으며 모듈 내부 Repository/ORM 직접 접근 예외를 추가하지 않는다. 담당 관계 인정(Pass의 잔여 0 외 상태/종료·변경/이력)과 필터의 다른 종료 상태별 잔여 정의/집계, 지원 지정/해제 절차·소속 이동의 권한/시점·이력·전화번호 외 공개할 Member/Pass/PT 정보와 실제 수업 등록의 나머지 인가는 MB/ARCH/LEGAL 게이트 후속이다. 조회 허용으로 보상 설정·다른 Trainer의 전체 PT 정보/쓰기 권한을 자동 공개하지 않는다. 관리자 겸임자의 별도 관리 Scope를 유지하고 조회/관계 변경 경합·실패 시 범위 밖 정보가 노출되지 않는 일관성은 계약 후 검증한다.

Trainer의 회원 전화번호 필드 공개(2026-10-12 Product 확정, BR-OPS-005·PR-002/029/030·NFR-001/005): 현재 Caller의 담당/개별 지원 관계와 Organization Scope로 인가된 Member에 대해 등록된 전체 전화번호를 읽을 수 있다. 잔여 0에도 기존 관계 인가가 유지되면 동일 적용하고 지원 해제 후 독립적인 담당/관리 권한이 없으면 번호를 반환하지 않는다. 목록/검색/직접 ID·필드 선택을 통한 미인가 회원 번호 노출을 허용하지 않는다. 현재 Caller/관계 사실과 최소 Member 응답을 Membership 공개 계약으로 조합하는 안은 PROPOSED이며, 관계 철회/담당 변경과 조회의 실패·경합/응답 일관성은 후속 검증한다. 번호 읽기를 수정/내보내기·다른 개인정보/개별 Pass·다른 Trainer 보상 권한으로 확대하거나 조회 승인으로 필수 수집/저장 형식·중복·보존 정책을 결정하지 않는다. 구체 계약/필드·저장/UoW 및 그 외 Product/LEGAL 게이트는 유지하고 직접 DB 읽기 예외를 추가하지 않는다. 운영 전화번호를 일반 로그/문서에 복사하지 않고 가상 데이터로 검증한다.

회원 전화번호 필수 입력(2026-10-12 Product 확정, BR-OPS-006·PD-022·PR-002·NFR-005): 새 Member 등록은 전화번호를 필수로 받으며 누락·빈값·공백만인 요청을 Backend에서 거부하고 등록 성공으로 확정하지 않는다. 일반 수정으로 필수 번호를 비우는 변경도 사용자 일관성 지시를 적용해 거부하고 요청 직전 번호를 유지한다. 다른 정보만 수정할 때는 기존 번호를 유지하며 임의 기본 번호로 누락값을 채우지 않는다. 업무 Role·Scope 검증과 필수 값 검증은 각각 필요하며 이 입력 조건으로 Trainer 등에게 등록/수정 권한을 추가하지 않는다. 앞 문단의 전화번호 조회 승인과 별도로 필수 입력만 후속 승인됐고 형식·중복/인증·다른 필드·보존/필요 삭제는 게이트를 유지한다. 구체 오류 응답·입력 형태·저장 제약과 등록/수정 UoW는 PROPOSED/후속 설계이며 직접 DB 접근 예외를 추가하지 않는다.

회원 전화번호 중복 허용(2026-10-12 Product 확정, BR-OPS-006·PD-022·PR-002·NFR-005): 동일 Organization에서 전화번호가 같은 Member를 각각 등록할 수 있고 별도 고유 식별자로 구분한다. 일반 수정에서도 번호 중복만으로 거부하지 않는 원칙은 기존 사용자 일관성 지시를 적용한다. 회원의 고유성/Pass·PT 이력·담당/지원 관계 또는 조회 권한을 전화번호 일치로 결정하지 않는다. 번호가 같다는 이유로 자동 병합하거나 기존 회원을 재사용하지 않으며 입력 번호의 동일성만으로 신규 회원을 막는 저장 제약은 승인된 중복 허용과 맞지 않는다. 전화번호 검색을 제공하면 현재 Caller가 조회할 수 있는 회원 집합에서 각각 식별하고 범위 밖 회원 존재를 중복 검사로 노출하지 않는다. 기존 전화번호 필수 입력·업무 Role/Scope·Member 로그인 Future Scope는 유지한다. 저장 식별자/열/인덱스·응답/검색/정규화·UoW는 계속 PROPOSED/후속 설계다. 앞 문단의 당시 미결정 중 중복 허용만 이번 후속 승인으로 해결됐으며 번호 형식/검증·다른 필드·보존/필요 삭제는 해당 게이트를 유지한다. 직접 DB 접근 예외는 추가하지 않는다.

잔여 0 회원 조회와 선택 제외 필터(2026-10-12 Product 확정, BR-OPS-005·PR-002/029/030): 담당 Pass 잔여가 모두 0이어도 기존 담당 회원 조회를 차단하지 않고 기본 조회에 포함하며 선택 “잔여 0인 회원 제외” 필터를 제공한다. 인가된 Member 집합 안에서 조회 조건을 적용하고 필터 해제/직접 ID 요청도 기존 Caller/Organization·담당/지원 관계 인가로 검증한다. 필터는 관계 철회·회원 상태 변경이나 PT 차감 조건 완화가 아니며 과거 기록/Remaining을 바꾸지 않는다. 필터는 인가된 Member 전체 Pass 잔여(다른 담당 Trainer/Issued Branch 포함)이며 개별 지원 회원도 같은 기준으로 후속 확정됐다. 다른 종료 상태별 잔여 정의/집계·다른 조회 상태/필드는 Product 게이트다. 잔여 사실은 PT Operations 소유권을 유지하고 공개 계약을 통한 회원 조회/선택 필터·검색/페이지/집계 조합을 후속 설계한다(PROPOSED). 다른 모듈 Repository/ORM 직접 접근 예외와 구현된 endpoint/파라미터를 추가하지 않는다. 조회/차감·잔여 조정 경합 및 실패 시 인가/조건/반환 결과의 일관성은 후속 계약 후 검증한다.

필터용 회원 전체 잔여 집계(2026-10-12 Product 확정, BR-OPS-005): 먼저 현재 Caller/Organization·담당/개별 지원 관계로 인가된 Member 집합 안에서 해당 Member 전체 Pass 잔여를 판단한다. 다른 담당 Trainer/Issued Branch를 집계 대상에서 제외하지 않고 개별 지원 회원도 같은 Member 기준이다. 내 담당 0회/다른 담당 10회이면 표시하고 전체 0회이면 선택 필터에서 제외한다. 수동 만료의 보존된 양수 잔여를 0으로 간주하지 않고 실제 PT 사용 가능성 판정과 분리한다. 원천에서 확인된 보유 Pass 없음은 합계 0이지만 미조회/실패/불완전한 사실은 0으로 대체하지 않는다. PT Operations 소유 잔여를 공개 조회 계약으로 확인하고 Member 필터·검색/페이지·집계와 조합하는 안은 PROPOSED다. 계약의 반환 형식(집계 횟수/조건 사실 등)·현재 잔여와 결과의 일관성/실패·동시성 및 다른 종료 상태의 잔여 정의/공개 필드는 후속이다. 이 필터 결정만으로 개별 Pass/다른 Trainer 내역·집계 숫자 화면 표시 권한을 넓히거나 타 모듈 Repository/ORM 직접 읽기 예외를 만들지 않는다.

개별 지원 대상 지정(2026-10-12 Product 확정, BR-OPS-005·PR-002/029/030): Master Organization 전체/Branch Admin 지정 시점 현재 관리 Branch=Member 현재 Home Branch에서만 허용한다. 검증된 Actor 현재 Scope·Member 소속과 대상 Trainer/Member의 Organization 관계를 확인하고 수행/Trainer Home/Pass Issued Branch·과거 소속/지정 Actor 사실로 대체하지 않는다. 같은 Organization의 타 지점 Trainer도 대상이 될 수 있으나 그 Trainer 보상/전체 정산·전체 회원 조회 권한이나 Home Branch 변경을 부여하지 않는다. 지정과 NFR-004 필수 감사의 일관된 저장, 권한 없는 거부/실패 시 직전 허용 관계·조회 범위/기존 기록 유지, Actor Scope/Member Home Branch 변경·지정/조회 경합을 보장할 공개 계약/UoW·저장/잠금은 후속 설계(PROPOSED)다. 지정 권한과 감사 원칙이 지원 허용 소유 모듈/테이블·계정 역할 모델을 결정한 것은 아니며 직접 DB 접근 예외를 추가하지 않는다. 소속 이동 자체의 권한/시점·이력·대상 상태/지정·해제 절차·최소 Trainer 식별정보/회원 공개 항목은 잔여 게이트다.

개별 지원 조회 허용 기간(2026-10-12 Product 확정, BR-OPS-005): 관리자 해제 전까지 유지하고 고정 종료일/시간 경과 자동 종료·기간 연장을 두지 않는다. 수동 해제는 기존 지정과 같은 Master Organization/Branch Admin 각 처리 시점 Member 현재 Home Branch 인가와 NFR-004 감사를 적용한다(2026-10-11 사용자 일관성 지시). 해제 성공 후 해당 지원 관계를 근거로 한 후속 조회는 허용하지 않으며 별도의 담당/관리 권한은 독립 검증한다. 과거 PT·Pass 차감·지급/정산 변경 명령으로 취급하지 않는다. 현재 Caller/대상 관계 확인은 유지한다. 소속 이동 후 관계 유지/종료·대상 상태/절차/필드는 여전히 게이트이며, 소유권/저장 모델·공개 계약/UoW·해제와 조회/이동/실패 경합의 일관성은 후속 설계(PROPOSED)다. AuthSession 수명과 별개인 업무 조회 허용 정책이다. ADR-0004 v1 인증 방식은 후속 A1 답변으로 별도 승인됐다.

개별 지원 조회 허용과 Home Branch 이동(2026-10-12 Product 확정, BR-OPS-005): 동일 Organization 내 Member Home Branch 변경 후 기존 Trainer/Member 허용을 유지하고 재지정/자동 해제를 요구하지 않는다. 이동 후 지정/해제마다 검증된 Caller의 현재 관리 권한과 Member 현재 Home Branch·대상 Organization 사실로 인가하며 이전 Branch/지정 Actor 사실로 대신하지 않는다. Trainer Home Branch만 바뀐 경우도 사용자 일관성 지시로 같은 유지 원칙을 적용한다. 기존 허용/감사 이력을 보존하고 과거 PT·Pass·지급/정산 변경이나 보상 방식 고정 명령으로 취급하지 않는다. 이동 자체의 권한/적용 시점/이력/정정·다른 상태/필드 조건은 게이트다. 지원 허용·현재 Member 관계를 공개 계약으로 확인하고 이동과 지정/해제/조회 경합에서 현재 인가와 관계 일관성을 보장할 소유권/저장/계약/UoW·잠금/실패 처리는 후속 설계(PROPOSED)이며 직접 DB 읽기 예외를 추가하지 않는다.

추가실적 등록 흐름 정책(2026-10-11 사용자 확정): v1 추가실적은 권한 있는 관리자의 직접 등록만 지원하고 Trainer의 시스템 내 별도 신청·승인/반려 흐름은 두지 않는다. Trainer는 실적 내용을 관리자에게 전달하며 기존 Master Admin/Branch Admin이 허용된 관리 범위에서 입력한다. 기존 Master Organization/Branch Admin 대상 Trainer Home Branch 범위·관리 범위 안 본인 등록·별도 승인 없음·필수 감사를 유지한다. Trainer의 PT 진행 기록·지원 수업 Pass 차감과 이후 관리자 금액 저장은 기존 승인된 별도 업무 단계다. v1에 Trainer 신청 상태·승인/반려 명령을 추가하거나 PT 진행 기록을 보상 신청으로 취급하지 않는다. 관리자·Trainer 겸임자는 검증된 관리 권한으로 본인 직접 등록할 수 있다. 나머지 입력/금액 확정 시점·비지원 실적의 금액 외 정보 수정/취소의 이동 시 인가·정정/취소 등은 BR-013/010 등 OPEN이며 계약·저장/UoW·연계/동시성은 PROPOSED다.

지원 수업 외 추가실적 금액 정책(2026-10-11 사용자 확정): 회원 유지 등 지원 수업 외 Additional Performance의 금액도 권한 있는 관리자가 실적 건별로 직접 입력한다. v1에서 유형별 사전 금액·산식으로 자동 계산하는 방식을 채택하지 않으며 일반 RATE/FIXED_AMOUNT 계산 결과로 입력액을 대체하지 않는다. 기존 등록 역할/대상 Home Branch 관리 Scope·관리 범위 안 본인 등록·별도 승인 없음·필수 감사와 발생 당시 Home Branch 비용 귀속은 유지한다. Workforce의 건별 금액 입력 계약은 관련 정책 해소 후 설계하며 유형별 자동 산정이나 일반 Session Payment 계산으로 대체하지 않는다. 이 금액 방식만으로 지원 수업의 단계 분리/미입력 월 확정 차단·0원 정책을 다른 추가실적에 적용하지 않는다. 금액 확정 시점·미입력/0원·정산 월·비지원 실적의 금액 외 정보 수정/취소의 이동 시 인가·정정/취소는 BR-013/010 및 MB-010 등 OPEN, 저장·단계별 UoW·상태/연계·버전·동시성은 PROPOSED다.

지점별 비용 보고서의 Product 권한(2026-10-11 사용자 확정): v1 지점별 비용 보고서는 Master Admin만 Organization 범위에서 조회한다(2026-10-11 사용자 확정). Branch Admin은 자기 지점 비용 합계도 이 보고서로 조회할 수 없으며 Master 권한 없는 Operator·Trainer도 불가하다. Branch Admin의 현재 자기 Home Branch 소속 Trainer 해당 월 정산 전체 금액·구성 내역 조회는 타 지점 지원 보상까지 포함하여 유지한다. 비용 귀속·지급액·기존 등록/정정/확정 권한은 유지하며 보고서 항목·대상 월·집계/완전성·버전 등 남은 상세는 MB-006/010 OPEN이다. 보고서의 모든 개별·목록·검색·집계 조회 계약에서 검증된 Caller Context의 현재 Master 권한과 Organization Scope를 확인하는 안을 후속 설계한다. Master·Trainer 겸임은 허용하지만 Branch Admin·Trainer 겸임만으로는 허용하지 않는다. 비용 귀속 Branch를 인가의 대체값으로 사용하지 않는다. 이 결정은 직접 DB 읽기 예외를 추가하지 않으며 모듈별 소유 계약·구체 집계/저장/버전·조회 일관성은 PROPOSED다.

정산 조회의 Product 권한(2026-10-11 사용자 확정): Branch Admin은 조회 시점에 자신의 관리 Branch를 Home Branch로 가진 Trainer의 해당 월 정산 전체 금액과 구성 내역을 조회할 수 있다. 해당 월 적용 기본급·일반 Session Payment·타 지점 지원 수업을 포함한 Additional Performance·월 정산 총액을 모두 공개하며, 수업의 Performed Branch가 다른 지점이라는 이유로 해당 금액을 제외하거나 숨기지 않는다. 관리 범위 안 본인 Trainer도 포함하고 Master Organization 전체 조회는 유지한다. 수행 지점만을 근거로 다른 Home Branch Trainer의 전체 월 정산을 공개하지 않는다. 각 공개 조회 경로의 현재 Scope 검증과 허용된 구성 금액·내역 반환 계약을 후속 설계한다. 이 권한 승인은 다른 모듈 DB 직접 읽기 예외나 ORM/Repository 접근을 승인한 것이 아니다. 조회 대상 월·이전 확정본/세부 계산 근거·감사 공개의 남은 상세는 MB-006, 비용 귀속은 MB-010 OPEN이며 구체 계약·조회 일관성은 PROPOSED다.

예외 요청에는 소유자·소비자·필드·권한 필터·일관성·민감정보·제거 계획과 승인을 남긴다. 읽기 전용이어도 권한 우회나 현재 값으로 과거 금액 재계산을 허용하지 않는다. 최적화 없이도 correctness가 성립하는 계약부터 정의한다.

## 일반 Session 등록의 원자성

2026-10-12 Product 확정(BR-PAY-006): 소급 PT 등록의 차감 후보는 실제 수업 당시 이미 발급된 Pass로 한정하고 이후 발급된 것은 제외한다. 이 조건과 기존 사용 조건/인가를 만족한 후보에 FIXED_AMOUNT 우선/FIFO를 적용한다. 일반 지급 설정의 기록 생성 시점 기준과 혼용하지 않는다. PT Operations가 소유한 Pass 발급 사실과 실제 수업 시점을 확인하는 계약/조회·동시 발급/정정/차감 경합의 일관성을 후속 설계한다(PROPOSED). 발급 시점을 시스템 생성일/이용 시작일 중 무엇으로 저장/표현할지, 동일 일자 순서/시각 정밀도·발급 사실 확인 불가/정정·만료/종료/취소 상태 조건은 관련 게이트를 따른다. 수업 이후 Pass를 현재 보유한다는 사실로 수업 당시 발급 사실을 대체하지 않는다. 수동 만료 전 실제 수업 당시 사용 가능했던 Pass는 현재 만료 상태여도 기존 PT 권한·정산·현재 잔여 조건을 만족하면 해당 과거 수업 후보에 포함하는 것으로 Product 확정됐다(2026-10-12, BR-OPS-004). 현재 상태만을 일괄 필터로 삼아 이 후보를 제거하거나 사전 만료 해제를 요구하지 않는다. 후보 안에서 기존 FIXED_AMOUNT 우선/FIFO로 선택하고 현재 잔여에서 1회 차감/현재 만료 상태·이력 유지(만료/5회→만료/4회)를 보장한다. 당시 발급/사용 가능 사실과 현재 잔여/현재 Actor Scope·대상 월 상태를 구분하여 확인할 공개 계약과 원자적 기록/차감/필요 보상/감사·만료/해제·차감/월 확정 경합의 일관성은 후속 설계(PROPOSED)다. 과거 지급 설정으로 신규 일반 지급을 계산하거나 다른 종료 사유를 면제한 것으로 해석하지 않는다.

2026-10-11 Product 확정(BR-OPS-003): 해당 Trainer/실제 진행 월 정산이 미확정이면 Trainer는 기존 PT Scope에서 과거 수업도 직접 등록한다. 당월/최근 N일 제한을 추가하지 않는다. 일반 지급 설정은 신규 기록 생성 시점, 수업 구분은 실제 수행 당시 소속 기준을 유지한다. 요청 시 현재 Actor 권한/대상/Pass 사용 조건과 해당 Trainer/진행 월의 정산 상태를 확인하고 기록/차감/일반 지급/필수 이력과 월 확정 간 일관성을 보장하는 공개 계약·Application 조정 경계를 후속 설계한다(PROPOSED). Trainer에 정산 해제 권한을 추가하지 않으며 확정 월은 기존 관리자 해제 후 반영/재확정 원칙과 연계한다. 월 상태 확인 후 확정 경합·소급 Pass 선택 조건/과거 소속 확인·실패/재시도/UoW/잠금은 관련 게이트와 후속 설계 대상이다.

2026-10-11 Product 확정(BR-OPS-001): 일반/지원 구분은 실제 수업 당시 Trainer Home Branch와 Performed Branch 비교로 결정하며 이후 이동/등록 지연으로 바꾸지 않는다. 일반 PT 지급 설정은 기록 생성 시점, 보상/월 정산 인가는 처리 시점 현재 Home Branch 기준이므로 구분 사실과 혼용하지 않는다. Workforce의 당시 소속 사실을 공개 계약으로 확인하고 PT Operations의 수행 사실과 연결하는 방안을 후속 설계한다(PROPOSED). 과거 소속 확인 불가 시 현재 소속을 임의 대입하지 않는다. 이동 적용/이력 예외·소급 범위·사실 정정의 보상 전환/설정 시점은 MB-001/005·BR-007/008/013의 잔여 게이트이며 저장/스냅샷/동시성 방식을 이번 결정으로 확정하지 않는다.

FOUNDATION-001 용어: “PT 진행 등록”은 기존 회원에게 실제 수업을 수행했다는 완료 기록이며 상품/Pass 발급·미래 예약/시간표 생성이 아니다. 사전 Reservation과 PLANNED/BOOKED 상태는 필요하지 않다. 진행일과 기록 시점, 진행 기록 정정/취소와 예약 취소를 구분한다(PR-008/009, BR-008/BR-PAY-011). SQLAlchemy Session은 DB 자원이며 업무 PTSession과 별개다. 이번 기반에서는 이 업무 흐름을 구현하지 않는다.

대상은 일반 Session Payment 정책이 적용되고 업무 접근이 확정된 PTSession이다(PR-008, BR-PAY-006/008/011/012/013). MB-009의 타 지점 수업은 일반 PT 수당 대신 보상 전체를 Additional Performance로 처리하며 일반 Session Payment를 별도로 정산에 합산하지 않는다(2026-10-10 사용자 정정). 따라서 아래 일반 지급 계산·등록 시 지급 확정 흐름을 타 지점 수업에 그대로 적용하지 않는다. 실제 수업 기록·Pass 차감·감사는 유지한다. 타 지점 지원 수업은 보상 금액 없이도 허용된 PT 진행 기록과 Pass 차감을 먼저 완료한다. 권한 있는 관리자가 나중에 수업 건별 금액을 저장할 때 해당 Additional Performance 보상을 확정한다. 금액 미입력은 확정된 0원과 구분하고 누락 건을 추적할 수 있어야 한다. 해당 Trainer의 해당 월 정산 대상 지원 수업에 금액 미입력 건이 하나라도 있으면 그 Trainer·월 정산을 확정할 수 없다. 타 지점 지원 수업 보상은 권한 있는 관리자가 사유를 기록하면 0원으로 명시적으로 확정할 수 있다. 사유 없는 0원 입력은 보상 확정이 불가하다. 사유를 남기고 확정한 0원은 금액 미입력이 아니므로 그 건으로 월 정산 확정을 차단하지 않는다. 다른 미입력 건이 남으면 기존 차단 조건을 유지한다. 월 정산 확정 전 지원 수업 보상 금액 수정은 Master Admin에게 Organization 전체, Branch Admin에게 대상 Trainer Home Branch가 자신의 관리 Branch인 경우 허용한다. 관리 범위 안의 본인 건도 허용하고 변경 이력을 남긴다. 월 정산 확정 전 지원 수업 보상 금액 수정은 Master Admin·Branch Admin 모두 관리 범위 안에서 본인 건을 포함해 별도 승인 없이 저장 성공 즉시 반영한다. Master나 다른 관리자의 승인 대기를 두지 않으며 권한 검증과 변경 이력을 유지한다. 월 정산 확정 전 지원 수업 보상 금액의 모든 수정에는 변경 사유가 필수다. 양수 간 변경·0원에서 양수로 변경·양수에서 0원으로 변경 모두 적용하며, 사유 없이는 금액을 수정할 수 없다. 변경 전후 금액·변경 사유·수정자·수정 시점을 이력으로 남긴다. 확정된 월 정산에서 지원 수업 보상 금액 오류를 발견하면 해당 Trainer·월 정산의 확정을 해제하고 금액을 정정한 뒤 해당 월 정산을 다시 확정한다. 이전 확정본은 이력으로 보존한다. 지원 수업 보상 금액 오류 정정의 월 정산 확정 해제·재확정은 Master Admin은 Organization 전체 Trainer, Branch Admin은 자신의 관리 Branch를 Home Branch로 가진 Trainer에 대해 허용한다. Branch Admin이 자신의 관리 Branch를 Home Branch로 가진 Trainer의 지원 수업 보상 정정을 위해 월 정산을 확정 해제·재확정할 때는 Master의 별도 승인을 두지 않는다. Master 승인 대기 단계 없이 관리 범위 안에서 직접 처리하며 이전 확정본과 해제·재확정 이력 및 감사를 유지한다. 지원 수업 보상 정정의 월 정산 확정 해제에는 사유가 필수이며, 사유 없이 해제할 수 없다. 사유·해제자·시점을 이력으로 남긴다. 과거 지원 수업 보상 정정·해당 월 정산 확정 해제/재확정에서 Branch Admin의 권한은 각 업무 처리 시점의 Trainer 현재 Home Branch를 기준으로 검증한다. 이전 소속만으로 권한을 유지하지 않으며 Master Admin의 Organization 전체 권한은 유지한다. 남은 정정·취소 절차는 BR-009/013 등 관련 OPEN을 따른다. 각 단계의 경계는 아래 제안과 관련 게이트를 따른다. 일반 Session Payment를 0원으로 저장하는 모델은 이번에 선택하지 않는다. 금액 미입력 보상을 확정 0원으로 처리하지 않는다. 자동 초안 생성·행/상태값·테이블 구조도 이번에 확정하지 않는다.

이하 흐름은 일반 Session Payment 적용 대상이다. Application Use Case가 하나의 UoW를 소유하는 흐름을 제안한다.

1. 입력 어댑터에서 인증 결과를 확인한다. 업무 UoW 안에서 현재 Actor 계정/권한과 대상 Member·Trainer·Branch·Pass 이용 조건을 확인한다. Router에서 통과했다는 이유로 생략하지 않는다.
2. 해당 Member의 사용 가능한 Pass 후보와 각 Pass 발급 당시 상품 가격·총횟수·Payment Type을 확인한다. FIXED_AMOUNT 우선, 동일 Type FIFO로 소비 대상을 결정한다. 잔여 0은 제외한다. 선택과 차감 사이에 다른 요청이 후보 상태를 바꾸지 못하도록 일관성 전략을 후속 결정한다.
3. 같은 일관성 경계에서 수행 Trainer와 적용 Rate/Fixed Amount의 확정 근거를 확보한다. Base Salary는 Session 계산에 넣지 않는다. BR-011 CLOSED에 따라 상품 변경과 무관하게 소비 Pass 발급 당시 가격·총횟수·Payment Type을 사용한다. 발급 조건 보존 구조는 T-09 후속이다.
4. 소비 Pass 잔여 1회 차감, 실제 날짜·수행 Trainer·Performed Branch의 Session, 계산 근거와 확정 Session Payment를 함께 기록한다. RATE는 Session별 1,000원 올림, FIXED_AMOUNT/서비스는 해당 Fixed Amount 그대로다.
5. 필요한 감사와 재전송을 식별할 처리 결과를 같은 UoW에 기록하는 안을 검토한다. 필수 감사 실패를 무시하지 않는다. 멱등성 구조는 후속이지만 업무 효과와 성공 기록이 따로 commit되어서는 안 된다.
6. 모든 검증·변경이 성공했을 때 한 번 commit한다. 완료 확인 전 성공 응답을 만들지 않는다. 예외는 전체 rollback이며 일부 Repository만 성공으로 남기지 않는다.

| --- | --- | --- |
| Pass 잔여와 차감 근거 | PT Operations | 사용 횟수 보존 |

| 확정 Session Payment와 적용 근거 | PT Operations | 등록 시 지급 확정, 현재 설정 재계산 금지 |
| 필수 변경 감사 | Audit 기반 | 정상 성공한 변경의 추적 |
| 동일 요청의 완료/결과 기록(구조 후속) | PT Operations의 해당 Use Case 책임 | 응답 유실 재시도로 업무 효과 중복 방지 |

읽기로 참여하는 IAM·Organization·Membership·Workforce도 현재 권한/소속/설정 일관성에 결합된다. 단순히 같은 DB 트랜잭션이라는 사실만으로 경쟁 조건이 해결되지는 않는다. 결정한 격리/동시성 전략으로 확인 시점과 변경 시점의 유효성을 증명해야 한다.

일반 Session Payment 적용 대상에서 허용하지 않는 상태는 차감만 존재, 지급 결과 없는 정상 Session, 실패로 확정 처리한 요청의 부분 commit이다. 지원 수업의 승인된 금액 미입력 단계는 아래와 구분한다. **commit 후 통신이 끊겨 클라이언트가 성공을 못 받은 상황**은 별개다. 그 경우 전체 업무는 이미 성공했을 수 있으므로 응답 실패를 rollback 증거로 취급하지 않고 동일 작업 결과 조회/재요청으로 확인한다. 불명확한 commit을 새 작업으로 맹목 재실행하지 않는다. 검증은 timeout 전후 DB의 전체 결과를 대조한다.

2026-10-10 사용자 확정(지점 관리자의 지원 수업 보상 정정 시 월 정산 확정 해제·재확정의 별도 승인 질문의 1번 답변): Branch Admin이 자신의 관리 Branch를 Home Branch로 가진 Trainer의 지원 수업 보상 정정을 위해 월 정산을 확정 해제·재확정할 때는 Master의 별도 승인을 두지 않는다. Master 승인 대기 단계 없이 관리 범위 안에서 직접 처리하며 이전 확정본과 해제·재확정 이력 및 감사를 유지한다. 기존 Master Organization 범위·Branch Admin 대상 Trainer Home Branch 기준과 범위 밖 접근 거부는 유지한다. 해당 Trainer·월의 확정 해제 → 금액 정정 → 동일 월 재확정 순서와 재확정 시 미입력 지원 수업 차단 등 승인된 확정 조건도 유지한다. 이번 결정은 위 정정의 별도 Master 승인 생략에 한정하며 최초 월 정산 확정 권한/승인, Trainer 신청 승인, 다른 정정/취소 또는 정산 공개 범위로 확대하지 않는다. 확정 해제 사유 필수는 아래 후속 사용자 결정으로 확정했다. 위 지원 수업 보상 정정의 현재 Home Branch 권한 기준은 아래 후속 사용자 결정으로 확정했다.

2026-10-10 사용자 확정(지원 수업 보상 정정 시 월 정산 확정 해제 사유 질문의 1번 답변): 지원 수업 보상 정정의 월 정산 확정 해제에는 사유가 필수이며, 사유 없이 해제할 수 없다. 사유·해제자·시점을 이력으로 남긴다. Master Admin·Branch Admin 모두에 적용한다. 기존 Master Organization 범위·Branch Admin 대상 Trainer Home Branch 기준, Branch Admin의 별도 Master 승인 없음, 이전 확정본 보존과 해제·정정·동일 월 재확정 경로를 유지한다. 금액 수정의 변경 사유 필수도 유지한다. 사유 없는 해제 요청은 기존 확정 상태·확정본·보상 금액을 변경하지 않는다. 이번 결정은 위 지원 수업 보상 정정의 확정 해제에 한정하며 다른 정정/취소 정책으로 확대하지 않는다. 구체 입력 화면·저장 구조는 후속 Architecture 검토 대상이다.

| 정산과 원본 정정 경쟁 | 해당 Trainer·월의 미입력 지원 수업 존재 확인과 확정이 일관되게 수행됨. 지원 수업 등록/보상 저장/정정과 월 확정의 경쟁 검증. 확정 결과에 미정 소급 규칙을 적용하지 않고 동일한 입력 기준으로 대사 가능 | BR-007/009/012/013, MB-010 결정 후 월 경계/버전·정정 연동 |

잠금의 위치·순서, 낙관/비관 방식, 격리 수준, 실패 시 전체 재시도, 멱등성 저장/키/보존 기간은 후속 기술 결정이다. 잠금 하나 또는 기본 격리 수준만으로 위 결과를 보장한다고 주장하지 않는다. 실제 DB 경쟁 검증 없이 in-memory 시험만으로 완료 처리하지 않는다.

C9/C10/C12/C13 승인 반영: 실제 시작 시점의 Asia/Seoul 날짜/월과 기록 생성 시점의 일반 지급 설정을 구별한다. 참가자 오류는 원본 취소/Pass 복원·기존 지급/연계 AP 무효화와 올바른 재등록/새 Pass 선택·일반 지급 또는 지원 보상 단계를 정정 연결로 추적한다. 영향받는 각 Trainer·월 확정본은 기존 해제/재확정과 별도 Actor/Scope를 적용한다. 취소/재등록 단계 전체를 임의로 하나의 DB transaction으로 확정하거나 각 단계 중간 실패를 숨기지 않으며 정확한 순서/원자성·재시도 계약은 후속 설계다. 수동 조정과 실제 차감/복원이 경합해도 음수 잔여를 만들지 않고 수동 만료를 횟수 추가로 해제하지 않아야 한다. 실제 PostgreSQL 경합 검증은 아직 없다. ## 보상 설정 및 다른 업무의 트랜잭션

기존 Pass의 담당 Trainer 교체(2026-10-12 Product 확정, BR-OPS-008·PD-007·PR-003): 같은 Pass의 Assigned Trainer를 변경할 수 있고 잔여·발급 조건/Issued Branch·과거 실제 수행 Trainer/수업·확정 지급/정산은 보존한다. 취소/재발급이나 횟수 복원/재차감이 아니라 기존 Pass의 담당 변경 업무다. 일반 교체 저장 후 반영·전후 이력/감사는 기존 사용자 일관성 지시를 적용하며 변경 후 Member 조회는 현재 담당/별도 지원/관리 관계로 판단한다(BR-OPS-005). PT Operations의 Pass 담당 변경 명령을 IAM Caller·Membership의 최소 Member 사실·Workforce 최소 Trainer 사실 및 Audit 공개 계약과 조합하고 변경/이력/필수 감사를 한 Application UoW로 처리하는 안은 PROPOSED다. 다른 모듈 내부 Repository/ORM 직접 수정이나 보상 설정 조회 권한을 부여하지 않는다. 교체 권한은 Master Organization 전체/Branch Admin 처리 시점 Member 현재 Home Branch 기준으로 Product 확정(2026-10-12)됐다. 검증된 현재 Caller 관리 Scope·실제 Pass→Member 관계와 Member 현재 소속을 명령 인가에 사용하며 Issued Branch/Trainer Home/Performed Branch·이전 소속/처리자만으로 대체하지 않는다. 비관리자 Operator/Trainer·범위 밖 직접 ID/위조 Scope 요청은 거부하고 관리자 겸임은 관리자 Scope로 판단한다. 수동 만료/해제의 Issued Branch 기준과 보상 설정의 Trainer Home Branch 기준은 유지한다. 교체 대상은 같은 Organization의 다른 지점 Trainer도 허용으로 Product 확정(2026-10-12)됐으며 대상 Trainer의 실제 Organization 관계를 검증한다. 최소 Trainer 식별/소속 사실을 사용할 공개 계약은 별도 설계이며 이 사실 검증이 다른 지점 전체 Trainer 목록/프로필·보상 설정 조회 권한을 부여하지 않는다. 현재 담당 기반 회원 조회와 실제 수업 당시 수행 Trainer Home Branch/Performed Branch의 일반·지원 보상 구분을 유지한다. 교체 전 실제 본인 수업은 이전 담당 직접 누락 등록 허용으로 Product 확정(2026-10-12, BR-OPS-003/008)됐다. PT Operations의 과거 담당/Pass 이력과 현재 IAM Caller/본인 Trainer·Organization, 대상 Member/실제 수업 사실을 검증하며 현재 B 담당이라는 이유만으로 A 등록을 차단하지 않는다. 등록 명령의 한정된 인가와 회원 목록/상세·전화번호 조회 인가를 분리하며 최소 대상 식별/응답 경로는 후속 계약이다. 기존 과거 수업 등록 UoW·Pass 선택/현재 잔여 차감·미확정 월/관리자 해제 조건을 유지하고 신규 지급은 실제 수행 A의 등록 시점 설정, 일반/지원 구분은 수업 당시 A Home Branch/Performed Branch를 사용한다. A의 과거 담당 사실만으로 교체 후 새 수업이나 다른 Trainer 기록을 허용하지 않는다. 잔여 소진 0인 Pass도 담당 교체·새 현재 담당 Member 기본 조회를 허용한다(2026-10-12 Product 확정, BR-OPS-008). 잔여 0·발급 조건/Issued Branch·과거 수업/보상·상태는 유지하고 횟수 복원/추가·사용 재개나 정상 PT 차감을 만들지 않는다. 기존 현재 관계 인가/공개 필드·Member 전체 Pass 잔여 선택 필터와 변경 이력/필수 감사 원칙을 따른다. 상태를 저장/계산하는 표현 때문에 잔여 소진 완료 Pass를 임의로 교체 금지하지 않으며 상태명/저장 방식을 확정한 것은 아니다. 수동 만료/취소 등 잔여 소진 외 다른 상태·과거 담당/수행 사실 확인 불가/정정·다른 관계의 나머지 인가, 담당 교체/조회/수업 등록·소속/계정 상태의 경합과 실패/재시도·저장/응답/이력 계약은 후속 설계/검증 대상이다. 실제 수행 Trainer와 Pass 담당을 구별하고 과거 지급을 새 담당 기준으로 재계산하지 않으며 직접 DB 접근 예외를 추가하지 않는다.

회원 Home Branch 변경(2026-10-12 Product 확정, BR-OPS-007·PD-004·PR-002/030·MB-002): Master Organization 전체 또는 변경 전 Member 현재 Home Branch 관리 Branch Admin이 같은 Organization 내 이동을 처리하고 받는 지점의 별도 승인은 요구하지 않는다. 검증된 Caller의 현재 관리 권한/Scope·서버 Member 현재 소속·대상 Branch Organization 사실을 소유 모듈 공개 계약으로 확인하고 Membership 변경 명령을 조정하는 안은 PROPOSED다. 이동 대상 확인에 필요한 최소 Branch 사실 계약을 후속 설계하며 이번 결정으로 IAM-001의 지점 전체 조회 인수 범위나 다른 지점 업무 데이터 접근을 확대하지 않는다. 변경된 Home Branch 반영 이후의 Member 관리·지원 지정/해제는 새 현재 소속 기준이고 과거 처리자/이전 소속만으로 권한을 유지하지 않는다. 기존 지원/담당 조회 허용과 다른 발급/수행 지점 기준 독립 업무 Scope는 각각 기존 규칙을 따른다. Member 이동으로 Pass Issued Branch·잔여/발급/담당 사실·Trainer 소속·과거 PT/확정 지급/정산을 자동 변경하지 않는다. 중요 변경 이력/감사 원칙을 적용하며 대상 Member·전후 Home Branch·Actor/권한/Branch Context·시점을 추적한다. 변경·이력·필수 감사를 한 Application UoW에서 처리하고 인가/소속 변경 경쟁·실패/재시도를 일관되게 다루는 구체 계약/전략은 후속 설계다(PROPOSED). 이동 적용 시점·예약/소급·정정 및 대상 Branch 활성/비활성 조건은 Product 게이트로 남기며 직접 DB 접근 예외를 추가하지 않는다.

회원 Home Branch 변경의 즉시 적용(2026-10-12 Product 확정, BR-OPS-007·PD-004·PR-002/030·MB-002): v1의 변경은 저장 완료 즉시 새 현재 소속으로 적용하며 미래 적용일 예약 변경을 지원하지 않는다. 성공한 저장 이후 시작된 후속 요청의 Member 관리·지원 지정/해제는 새 Home Branch와 현재 Caller Scope를 검증한다. 재로그인/Frontend 캐시 갱신·다음 날 배치가 되어야만 새 소속으로 인가하는 설계는 이 즉시 적용 조건과 맞지 않는다. 저장 실패 시 기존 Home Branch/권한 근거를 유지하며 기존 독립 담당/지원 조회 및 발급/수행 지점 기준 업무·Pass/과거 이력 보존은 그대로다. Membership 변경+이력+필수 감사의 UoW와 현재 소속 사실 조회/캐시·성공 응답의 일관성, 이미 처리 중인 요청·동시 이동/변경 실패의 일관 순서는 후속 상세 설계/검증 대상이다(PROPOSED). 앞 문단의 당시 미결정 중 일반 이동 적용 시점/미래 예약만 후속 승인으로 해결됐고 과거 소속 이력의 오류 정정/소급·대상 Branch 상태·최소 Branch 사실/응답·저장 계약은 게이트를 유지한다. Trainer 이동 시점과 AuthSession 방식/철회 구현을 이번 결정으로 승인하거나 직접 DB 접근 예외를 추가하지 않는다.

회원 Home Branch 이동 대상의 활성 조건(2026-10-12 Product 확정, BR-OPS-007·PR-002/030·MB-002/008): 같은 Organization의 운영 중인 활성 Branch만 이동 대상으로 허용하며 비활성 대상은 Master/Branch Admin 모두 거부한다. Backend에서 대상 Branch의 현재 상태/Organization 원본 사실을 검증하고 거부 시 기존 Member 소속/지원 허용·Pass/과거 이력을 유지한다. Frontend 대상 목록이나 요청의 활성 표시만으로 판단하지 않는다. Organization 최소 Branch 사실 공개 계약과 Membership 변경 Use Case의 현재 권한/대상 상태 검증·이력/필수 감사 및 UoW를 조합하는 안은 PROPOSED며, 이동과 대상 Branch 비활성화의 경합에서 사실 확인/반영 순서와 실패 일관성은 상세 설계/검증 대상이다. 기존 저장 완료 즉시 적용/미래 예약 미지원·Actor/관리 Scope·이력 보존은 유지한다. 이번 승인은 새 이동의 대상 조건이며 Branch 비활성화 자체의 기존 Member/Trainer/Pass 처리·비활성 출발 지점 업무·재활성화/과거 조회를 확정하지 않는다. 상태 enum/저장·오류 응답/잠금 계약을 승인하거나 직접 DB 읽기 예외를 추가하지 않는다.

Organization 공통 상품 생성/수정(2026-10-12 Product 확정, BR-PAY-001/PR-006, MB-007 CLOSED): Master Admin만 Organization 범위에서 허용하며 Master 권한 없는 Branch Admin·Operator·Trainer는 불가하다. PT Operations의 상품 변경 Application Use Case에서 검증된 Caller Context의 현재 Master 권한과 Organization Scope를 확인하는 계약을 후속 설계한다(PROPOSED). 요청 role/Branch/Product ID나 이전 권한만으로 변경할 수 없으며 무권한 거부 시 Catalog와 기존 Pass/수업/지급/정산을 변경하지 않는다. 변경 조건은 새 Pass부터 사용하고 기존 발급 당시 조건·잔여·과거 이력은 보존한다(BR-011). 상품 변경/발급 경합에서 조건 혼합 없이 발급 조건을 보존할 계약·저장/UoW/동시성은 후속 기술 설계이며 상품 조회·Pass 발급의 나머지 Scope 부여/최소 식별·상태 조건이나 판매 재개 등 나머지 상품 상태/삭제 정책을 임의 확정하지 않는다. Pass 발급 Actor/역할별 지점 범위는 BR-OPS-010의 후속 사용자 승인을 적용한다. 다른 모듈 DB 직접 접근 예외를 추가하지 않는다.

상품 판매 중단의 영향(2026-10-12 Product 확정, BR-PAY-001/006·PR-006/003): 새 Pass 발급만 차단하며 기존 Pass는 기존 권한·잔여·사용 조건에 따라 계속 사용한다. 기존 Master 전용 상품 변경 권한을 판매 중단에 동일 적용하고 Pass 발급 Use Case에서는 현재 상품의 판매 가능 상태를 Backend에서 검증하는 계약을 후속 설계한다(PROPOSED). 기존 Pass 선택/차감에서는 Catalog 판매 중단만으로 일괄 제외하지 않는다. 판매 중단 자체는 기존 Pass 조건/잔여·사용 상태/이력을 변경하거나 개별 만료/잔여 0 등 다른 사용 불가 사유를 면제하지 않는다. 상품 판매 중단·새 발급/기존 Pass 차감 경합에서 신규 발급 차단과 기존 조건 보존/사용의 일관성을 검증할 공개 계약·저장/UoW/잠금·재시도는 후속 설계다. 상품 상태값/판매 재개·삭제 동작이나 새로운 모듈 간 DB 직접 접근 예외를 승인하지 않는다.

설계 후속(PROPOSED): IAM의 검증된 현재 발급 Caller/Scope와 Organization의 Branch 사실을 사용하여 Membership의 발급용 Member 공개 검색 계약을 조합한다. 검색은 업무 데이터를 변경하지 않고 선택 결과의 Member 식별자도 발급 시 현재 Organization/권한·대상 조건으로 다시 검증한다. 일반 Trainer 조회 계약을 Organization 전체로 넓히거나 다른 모듈 Repository/ORM·DB 직접 접근 예외를 추가하지 않는다. 응답의 이름·전체 전화번호·현재 Member Home Branch 공개는 후속 1번 사용자 승인을 적용한다. 현재 발급 Scope를 검증한 Membership 검색/최소 식별 계약과 Organization 소속 지점 사실로 승인된 필드만 구성하고 일반 상세/다른 개인정보/Pass/PT·보상/내보내기 권한으로 확대하지 않는다. 추가 공개 정보·최소 선택 응답/계약·검색어 처리/빈 검색 및 대상 상태 조건·선택/발급 간 권한/소속 변경 일관성은 후속이며 쿼리/저장/API를 확정한 것이 아니다. 새 Pass/발급 조건/필수 감사의 기존 정합성 원칙과 기존 Member/Pass/PT·지급/정산 보존을 유지한다(BR-OPS-010, NFR-001/005).

2026-10-12 사용자 확정(발급용 검색 결과 표시 정보 질문의 1번): 새 PT Pass 발급용 Member 검색 결과에는 이름·전체 전화번호·소속 지점을 표시한다. 소속 지점은 해당 Member의 현재 Home Branch이며 Caller 관리 지점/Pass Issued Branch/수업 Performed Branch와 구별한다. 같은 Organization의 타 지점 회원 검색 결과에도 동일하게 적용하고 부분 마스킹된 번호만 표시하도록 제한하지 않는다. 기존 이름·전화번호 일부의 Organization 전체 지점 검색과 현재 발급 역할/실제 Issued Branch Scope 인가는 유지한다(BR-OPS-010, PD-004/007/022, PR-002/003/030, NFR-001/005).

## 보상 설정 권한의 경계

아래 정책은 PROPOSED가 아니라 [BR-PAY-010](../product/business-rules.md#br-pay-010)의 확정 조건이다. 이를 소유 모듈 경계에서 검사하는 구조가 PROPOSED다.

| Actor | Rate / Fixed Amount / Base Salary 조회·변경 |
| --- | --- |
| Master Admin | 본인 포함 Organization 전체 Trainer 허용 |
| Branch Admin | 본인 포함 대상 Trainer Home Branch가 자신의 관리 Branch일 때만 허용 |
| 관리자 권한 없는 Operator | 불가 |
| 관리자 권한 없는 Trainer | 본인 포함 불가 |

2026-10-10 사용자 최종 정정에 따라 Trainer 겸임 자체는 해당 계정의 관리 범위 안에서 본인 설정을 조회·변경하는 데 대한 거부 사유가 아니다. Branch Admin·Trainer의 본인 Home Branch가 관리 Branch와 다르면 본인도 불가다. 이는 보상 설정에 관한 확정 정책이며 다른 업무의 미정 권한을 자동 허용하지 않는다.

수원점 소속 Trainer가 강남점에서 지원 수업했어도 강남점 Admin에게 설정 권한은 없다. 허용된 설정 변경은 Master의 별도 승인 없이 가능하고 대상 Trainer·항목·전후 값·Actor·권한/Branch Context·시점을 감사한다.

인증 어댑터는 신원을 확인하고, IAM은 현재 계정/역할/Scope 사실을 제공하며, Workforce Use Case는 대상 Trainer Home Branch와 행위를 검사한다. 직렬화 전 허용 필드를 제한한다. Router 외 내부 명령·향후 배치·관리 호출도 동일한 인가된 Use Case 경로를 사용한다. 호출자가 임의로 Actor나 시스템 목적을 지정해 권한을 상승시킬 수 없게 진입점과 내부 계약을 분리한다.

PT 계산을 위한 내부 Rate/Fixed Amount 소비는 Trainer에게 설정 조회 권한을 주는 기능이 아니다. 승인된 Session 등록의 계산에 필요한 값만 신뢰 가능한 내부 호출에서 사용하고 그 값·계산 근거를 Trainer 응답에 그대로 전달하지 않는다. Settlement 내부 소비도 공개 열람 권한과 별개다. Branch Admin의 현재 소속 Trainer 해당 월 전체 금액·구성 내역 공개는 2026-10-11 별도 사용자 결정으로 확정했으며, 나머지 공개 상세는 MB-006 결정이 필요하다. Base Salary/추가실적 입력은 각 OPEN 해소 후 계약을 구체화한다.

오류 메시지·응답 DTO·일반 로그/trace·감사 검색/집계에 민감값이 새지 않는지 검증한다. 감사 원본은 필요한 전후 값을 보존하되 업무별 인가를 통과한 조회만 제공한다. “정산 조회 가능”을 설정 원본/추론 가능 근거의 무제한 공개로 확대하지 않는다. JWT/Cookie Session/OAuth 또는 인증 라이브러리는 아직 선택하지 않는다.

수업 취소/보상 무효의 원자성 후보(2026-10-11 Product 확정 반영): 기존 상위 조정 경로에서 PT Operations의 허용된 취소·Pass 복원과 Workforce의 해당 수업 보상 무효 및 필수 이력/감사를 취소 단계의 한 UoW로 조정하는 안은 PROPOSED다. 취소 성공인데 해당 수업 보상이 여전히 유효한 부분 결과는 Product 기대 결과를 충족하지 않는다. 원래 보상 금액·이력과 이전 월 확정본을 보존한다. 실제 계약/저장 표현·실패/재시도·금액 입력/취소/재확정 경합은 후속 설계·PostgreSQL 검증 대상이다. 정산 해제 → 취소 → 재확정의 담당 순서는 기존 Product 결정을 따른다.

N1/N2의 확정 추가 제한(BR-PAY-021): 비관리자 Trainer 본인 수업의 일반 지급/수업 연결 지원 보상 금액과 현재 다른 Home Branch Trainer 수업 금액을 해당 Performed Branch Admin에게 공개하지 않는다. PT 기록/정정의 인가와 금액 공개는 별도로 현재 Caller/실제 Trainer 현재 Home·행위별 관리 Scope를 확인한다. 내부 지급 확정/정산 소비·원본 보존을 유지하고 PT 등록 성공/목록/직접 ID·중첩/제공되는 집계·오류/감사로 같은 금액이 새지 않도록 최소 응답을 구체화한다. 비공개를 가짜 0원/삭제/재계산으로 표현하지 않는다. Master Organization/현재 Home 기반 기존 보상·정산 업무/겸임 독립 권한을 유지하고 다른 PT 기록 전체나 미결정 상태/필드의 공개는 추가하지 않는다. 응답 분리·내부 계약/현재 소속·역할 변경과 조회의 UoW/경합은 PROPOSED이며 직접 다른 모듈 DB 읽기 예외는 여전히 승인 0건이다. [N 승인](../product/product-decisions.md#review-20261013-n-batch); V-108/109 미구성·미실행.

## 미래 분리 제약

공개 계약 뒤 DB 어댑터가 같은 트랜잭션에 참여한다는 것은 현재의 실제 결합이다. Workforce를 외부 서비스로 바꾸면 설정 적용 순서, Membership/IAM을 분리하면 권한/소속 경쟁 검증이 달라진다. Audit을 비동기 외부 기록으로 바꾸면 필수 감사의 함께 성공/실패 조건이 달라진다. 이 결합을 해소하는 승인 정책·실패 복구 검증 전에는 분리하지 않는다. 상세 [추출 검토](module-boundaries.md#extraction)를 따른다.
